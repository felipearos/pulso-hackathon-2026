## What happened

Third session of this iteration. CI came back green on `d06110e` (build 93),
so this session worked §5.5–§5.6 and found two things: one open Codex thread,
and the branch `CONFLICTING` again because #98 had merged during the wait.

The Codex P2 was real and sharper than its own wording. The webhook claims
Meta's message id before processing and answers 200 immediately, so Meta never
redelivers on its own; a failed SQLite write therefore did not lose a retry, it
lost **the message permanently**, because every later delivery of it was
discarded as a duplicate. Fixed: a failed handler gives the id back
(`release` on `WebhookDeps`, `store.releaseWhatsappId`). The entrante and its
decision are one transaction, so a rejection means nothing landed and
re-claiming is safe; a `release` that throws is logged and nothing more,
because that task must never reject. Two webhook tests and one store test pin
it. The other half of Codex's suggestion — persist the pending body before the
200 with a work marker and our own retry — was declined on the thread: that is
an outbox, more machine than #48 asks for hours before the delivery.

The rebase onto #98 hit the **third migration-version collision of this one
ticket**: #90 had taken 3, #94 took 4, #98 took 5. Renumbered to 6. It is never
a textual conflict, which is what makes it dangerous — `migrate` keys applied
steps by version, so on the operator's PC, where the database survives every
deploy, `mensajes_procesados` would simply never have been created and the
webhook would have died on its first delivery, with a green suite, because an
in-memory base always starts from zero. Recorded as a third sighting on the
learning `migration-version-raced-by-parallel-prs` (fix ticket #106). #98's own
step test asserted the whole pending migration tail (`[5]`) rather than its own
step, so version 6 turned it red; scoped it the way its sibling test already
does.
